# Implementation plan: SGW Storm Preparation Prototype (Lighthouse 1)

> Take-home challenge for the role of AI Solution Engineer (Zug). Not an official AECOM document. SGW is a fictional client; all data is synthetic.

This plan is written for a coding agent (Claude Code). Work through the milestones in order. Each milestone ends with acceptance criteria that must pass before the next one starts. When the plan and the code disagree, the plan wins; when the plan is silent, choose the simplest option and record it in `docs/decisions.md`.

## 0. What we are building, in one paragraph

A local web app for the Emergency Operations Center (EOC) of a fictional utility, 72 hours before a hurricane lands. Five synthetic hurricane advisories are replayed one at a time. On each advisory the backend computes hazard exposure and a transparent risk score for about 200 assets, and an **advisory-cycle agent** checks the situation against the utility's hurricane playbook and produces a **decision package**: what changed, what the playbook requires, gaps, conflicts, and a draft situation report. A human approves or overrides each item; every step is written to an audit log. A chat copilot answers follow-up questions using tools. An optional calibration view shows the fragility parameters being fitted to a past storm.

**The prototype prepares; it never acts.** No AI output changes operational state without a human approval recorded in the decision log.

### Non-goals (do not build)
- Optimisation or crew routing of any kind (named as lighthouse 2 in the roadmap)
- Data pipelines, bronze or silver layers: data arrives as gold-layer JSON
- Authentication, multi-user, cloud deployment, streaming
- Real geography, real utility or facility names, real customer data

## 2. Data model

### 2.1 Gold files (generated by `scripts/generate_data.py`, seed 42)

**assets.json** (about 200 rows): `id` (`SUB-01`…, `PS-01`…, `WTP-01`), `name` (fictional), `type` (`substation` | `pump_station` | `treatment_plant`), `lat`, `lon`, `elevation_m` (nullable: 3 rows null on purpose), `distance_to_coast_km`, `install_year`, `condition_score` (1 good … 5 very poor), `last_inspection_date`, `customers_served`.
Mix: about 120 substations, 75 pumping stations, 1 treatment plant. Distribution assets are out of scope (PRD assumption A10).

**dependencies.json**: `from_id` → `to_id`, `to_kind` (`asset` | `facility`). Substations feed pumping stations, the treatment plant and facilities. Pumping stations feed the treatment plant.

**critical_facilities.json** (about 30): `id` (`HOSP-01`…, `SHEL-01`…), `name`, `type` (`hospital` | `shelter`), `lat`, `lon`. The treatment plant is an asset, but also counts as a critical facility type `treatment_plant` for P-4.5.

**staging_areas.json** (5): `id` (`STG-01`…), `name`, `lat`, `lon`, `elevation_m`, `distance_to_coast_km`. Exactly one (`STG-02`) is coastal and floods from advisory 4.

**fragility_curves.json**: one row per `asset_type` × `hazard` (`wind` | `flood`): `theta` (median capacity, mph or m), `beta` (dispersion). These are the "published" curves. The generator also holds hidden **true** parameters (never written to gold) used only to simulate Storm Delta outcomes.

**advisories/adv_NN.json**: `advisory_no`, `issued_at` (ISO), `hours_to_landfall` (72, 60, 48, 36, 24), `track` (list of `{t_hours, lat, lon, vmax_mph, rmax_km}`, 6-hourly to 24 h after landfall), `cone_radius_km` (by lead time), `landfall` (`lat`, `lon`), `peak_surge_m`.
The storm strengthens slightly and the track shifts east between advisories 2 and 4, so the ranking visibly reorders.

**initial_state.json**: operational state at advisory 1, keyed by entity: `inspection_completed`, `generator_assigned`, `barrier_installed`, `backup_power_confirmed`, `chem_stock_confirmed`, `boil_water_notice_ready`, `critical_customer_contacted`, `hospital_backup_confirmed`, `relocated`; event-level `generators_fuelled` (start at 6), `regulator_notified: false`, `activation_level: monitor` (declared at the start of the scenario).

**coastline.geojson**: a synthetic, gently curved coastline and land polygon for "Bayport County" (no real geography).

**history/**: a past fictional storm, "Storm Delta", with its best track and `outcomes` (`asset_id`, `failed: bool`) simulated from the hidden true parameters.

## 3. Scoring specification

All parameters live in `config/scoring.yaml`; nothing is hard-coded.

**Wind (modified Rankine vortex).** For each hourly-interpolated track point at distance r from the asset:
`V(r) = Vmax · r/Rmax` for r < Rmax, `V(r) = Vmax · (Rmax/r)^α` for r ≥ Rmax, α = 0.5. Reduce by 15% for points over land more than 10 km from the coast (simple inland decay). Asset wind = maximum over the track.

**Surge and flood depth.** Local surge = `peak_surge_m · exp(-(s/(2·Rmax))²) · exp(-d/L)`, where s is the alongshore distance from landfall, d the distance to coast, L = 3 km. Flood depth = max(0, local surge − elevation). Null elevation: impute the median of the 5 nearest assets and lower confidence.

**Ensemble.** 50 members: shift the whole track perpendicular to its heading by `N(0, σ)` with `σ = cone_radius_km` (seeded per advisory). The NHC cone is sized so the centre stays inside it about two-thirds of the time, which for a normal cross-track error means σ is roughly the cone radius. In production, consume the NHC probabilistic products (wind-speed probabilities, P-Surge) instead of this approximation; note this in `assumptions_limitations.md`, together with the simplifications that surge height and elevation share one datum and that wind is treated as 1-minute sustained. Compute exposure per member; report P50 and P90; failure probability is the mean over members.

**Fragility.** `P(fail | x) = Φ(ln(x/θ)/β)` per type and hazard. Condition adjustment: `θ_adj = θ · (1 − 0.075 · (condition_score − 1))` (up to −30%). Combine: `p_fail = 1 − (1 − p_wind)(1 − p_flood)`.

**Consequence.** `customers_served` plus downstream customers (one hop) plus policy weights from `consequence_weights.yaml` (hospital 5,000, treatment plant 20,000, shelter 1,000 customer-equivalents, editable). Unit: customer-equivalents.

**Risk and rank.** `risk = p_fail · consequence`; rank descending. Store a factor breakdown for the explain panel: wind exposure, flood exposure, fragility, condition adjustment, consequence components.

**Confidence.** `high` by default; `medium` if last inspection is over 3 years old; `low` if elevation was imputed. Never changes the score.

**Alerts.** Raise when risk crosses `alert.risk_threshold`, an asset enters the top 10, or an asset rises 10 or more places since the previous advisory.

## 4. The advisory-cycle agent

A LangGraph `StateGraph`, run automatically by `POST /advisories/next` after scoring completes.

| Node | Type | Does |
|---|---|---|
| `load_context` | deterministic | Advisory, scores, previous scores, op_state, activation level |
| `diff` | deterministic | Top-10 entries and exits, largest rank moves, new alerts |
| `retrieve` | deterministic | BM25 over playbook clauses, filtered by activation phase and asset types in the top 25; returns clause text + IDs |
| `evaluate_rules` | deterministic | Runs `playbook/engine.py` over `playbook_rules.yaml`; produces findings: actions, gaps, conflicts (prohibition blocks field work on same entity, cite P-8.2), and activation proposals (P-2.5) |
| `draft` | LLM | Narrative of what changed and why, findings explained with clause and asset IDs, draft sitrep marked DRAFT. Template provider gives a deterministic version |
| `validate_citations` | deterministic | Every clause ID and asset ID in the text must exist and match a finding or a retrieved clause; on failure, retry once, then fall back to the template draft |
| `await_approval` | interrupt | Human approves or overrides each item (override needs a reason); approvals update `op_state` and are logged; conflicts can only be decided by the IC role |
| `finalise` | deterministic | Persist package, decisions, sitrep status, audit events |

Rules for the agent:
- The LLM never decides whether a rule is met, never changes scores, and never writes `op_state`.
- The activation level is never set by code. A P-2.5 proposal appears at the top of the package; the commander declares it with one click (`POST /activation/declare`), which is logged as a decision and starts the P-7.2 clock.
- Every node writes an `audit_event` with input hash and versions (model version, rules version, prompt version).
- Prompts live in `backend/app/agent/prompts/` as versioned files.

## 5. Copilot (chat)

Tool-calling over the same services: `list_top_risks(advisory, n)`, `get_asset(id)`, `explain_score(id, advisory)`, `get_dependencies(id)`, `search_playbook(query)`, `get_decision_package(advisory)`, `get_findings(advisory, status)`. Answers must cite asset and clause IDs returned by tools. The template provider supports a fixed set of intents (why ranked, top risks, what depends on X, what does clause Y say) so the demo works offline.

## 7. Milestones

### M0. Scaffold (0.5 day)
`uv` project, FastAPI with `/health`, Vite React app, `docker-compose.yml`, `Makefile` (`make data`, `make dev`, `make test`, `make demo-reset`), ruff + mypy, pytest. Disclaimer footer component in the UI.
**Done when:** `docker compose up` serves both apps; `make test` passes.

### M1. Synthetic data, contracts, loader (1 day)
Generator per section 2 with all demo seeds. Pydantic models per gold file, exported to `contracts/`. Loader validates, rejects bad rows into a quality report, writes `lineage`.
**Done when:** `make data` is reproducible (same hashes on rerun); loader test rejects exactly the 2 bad example rows; seed tests in section 8 that only need data pass.

### M2. Hazard exposure (1 day)
Wind, surge, ensemble, `tsforce_arrival_h`.
**Done when:** unit tests: wind equals Vmax at Rmax and decays monotonically beyond; flood depth zero above surge height; P90 ≥ P50; same seed gives same numbers.

### M3. Risk score, alerts, replay (1 day)
Fragility, condition, consequence, risk, rank, confidence, factors, alerts. `POST /advisories/next` advances 1 → 5; `reset` returns to before advisory 1.
**Done when:** tests: p_fail in [0, 1] and monotonic in exposure; poor condition never lowers p_fail; top 10 changes between advisories 2 and 4; explain factors reproduce the stored risk.

### M4. Dashboard (1.5 days)
Map (coastline, assets coloured by risk, facilities, staging areas, forecast track and cone), ranked list with rank-change arrows, advisory stepper with hours-to-landfall, alert panel, asset explain panel (factor bar chart, confidence badge, dependencies), lineage and data quality page.
**Done when:** stepping 1 → 5 visibly reorders the list and recolours the map with no page reload.

### M5. Playbook retrieval and rule engine (1 day)
Parse `docs/playbook.md` into clauses (ID, section, text). BM25 index with phase and asset-type metadata. Rule engine implementing the semantics at the top of `playbook_rules.yaml`, including `value_field`, `contains_any`, deadlines and prohibition blocking.
**Done when:** engine unit tests cover every rule in the YAML; the seed tests in section 8 pass on the engine alone.

### M6. Advisory-cycle agent and decision package (2 days)
Graph per section 4, LLM provider interface with Anthropic, Azure OpenAI and template implementations (`LLM_PROVIDER`, `LLM_MODEL`, keys from env). Decision package UI: "What changed", "Playbook actions", "Gaps", "Conflicts (IC decides)", "Draft sitrep"; approve or override with reason; approvals update state and appear on the next advisory.
**Done when:** with `LLM_PROVIDER=template` the full demo runs offline; citation validator test rejects an invented clause ID; no code path lets the LLM write `op_state`.

### M7. Copilot chat (0.5 day)
Chat panel, tools per section 5, citations rendered as clickable chips that open the asset or clause.
**Done when:** "Why is PS-14 ranked where it is?" answers with factors and IDs in both template and LLM mode.

### M8. Audit timeline, sitrep approval, calibration (1 day, should)
Audit timeline view (filter by actor). Sitrep approval flow. Calibration: `fragility_prior.yaml` starts about 20% off the hidden truth; back-test on Storm Delta; reliability chart (10 bins), Brier score and top-decile capture before and after; fit θ and β per type and hazard by MAP (lognormal priors centred on the prior file); result saved as a `proposed` model version that a human approves before it is used.
**Done when:** after calibration, the Brier score improves and the approved version changes the scores on the next replay.

### M9. Documentation and demo readiness (0.5 day)
README (run steps, screenshots), `architecture.md` (map prototype components to the PRD's five layers and four planes), `assumptions_limitations.md`, `demo_script.md` (section 8 scenario, with timings for an 8-minute video).
**Done when:** a fresh clone runs with `docker compose up` and `make demo-reset`, and the demo script works end to end in template mode.

## 8. Demo scenario contract (end-to-end tests)

| Advisory | Hours | Must be true |
|---|---|---|

The test must also pass the alternative path where PS-14 is inspected at advisory 3 (then no conflict at 5).

## 9. Working agreements for the coding agent

- Run `make test` before every commit; keep commits small, one milestone step each.
- Do not change thresholds in `playbook_rules.yaml` or clause text in `playbook.md`; if a demo seed fails, fix the generator, not the rules.
- No real place names, utility names or people. All UI text and docs carry the disclaimer.
- Deterministic first: every LLM feature must have a template fallback and must work with no network.
- Log decisions you had to make in `docs/decisions.md` (date, decision, reason).
- Keep the UI plain and fast; clarity beats polish (the brief values practical thinking over production-ready polish).
